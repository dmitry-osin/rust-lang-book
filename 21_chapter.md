### Глава 21. Тестирование и Документация

#### 1. Введение в юнит-тесты

**Юнит-тест (Модульный тест)** — это маленькая программа, которая проверяет одну конкретную шестеренку в твоем механизме (например, одну функцию). Мы даем функции известные входные данные и проверяем, совпадает ли результат с нашими ожиданиями.

В Rust тесты пишутся прямо в том же файле, что и основной код. 

Давай напишем функцию для сложения чисел и сразу же протестируем её:

```rust
// Наша обычная функция бизнес-логики
pub fn add_two(a: i32) -> i32 {
    a + 2
}

// ---------------------------------------------------------
// ЗОНА ТЕСТИРОВАНИЯ
// Атрибут #[cfg(test)] говорит компилятору: "Компилируй этот модуль 
// ТОЛЬКО когда я запускаю тесты. Не включай его в готовую программу!"
#[cfg(test)]
mod tests {
    // Импортируем всё из родительского модуля (включая функцию add_two)
    use super::*;

    // Атрибут #[test] превращает обычную функцию в тестовую
    #[test]
    fn it_adds_two_correctly() {
        let result = add_two(2);
        
        // Макрос assert_eq! (Утверждать равенство) сравнивает два значения.
        // Если result НЕ равен 4, макрос вызовет panic!, и тест будет ПРОВАЛЕН.
        assert_eq!(result, 4); 
    }

    #[test]
    fn another_test() {
        let is_active = true;
        
        // Макрос assert! проверяет, что внутри true. 
        // Если там false - тест падает.
        assert!(is_active); 
    }
}
```

**Как это запустить?**
Ты просто открываешь терминал и пишешь команду:

```bash
cargo test
```

Cargo сам найдет все функции с пометкой `#[test]`, запустит их параллельно и выдаст красивый отчет:

`test tests::it_adds_two_correctly ... ok` <br>
`test tests::another_test ... ok`

#### 2. Тестирование ошибок (Как проверить, что программа паникует)

Иногда правильное поведение программы — это экстренная остановка (`panic!`). Например, если мы пишем игру, и здоровье персонажа падает ниже нуля, наша функция должна запаниковать, чтобы не пропустить этот баг дальше.

Как протестировать панику? Если мы просто вызовем такую функцию в тесте, тест упадет! Нам нужен специальный атрибут **`#[should_panic]`** (Должно запаниковать).

```rust
pub struct Guess {
    value: i32,
}

impl Guess {
    pub fn new(value: i32) -> Guess {
        if value < 1 || value > 100 {
            // Эта паника - ожидаемое поведение при неверных данных
            panic!("Значение должно быть от 1 до 100, а получили {}", value);
        }
        Guess { value }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    // Мы говорим тесту: "Твоя задача - упасть в панику. 
    // Если ты выполнишься без ошибок, значит функция работает неправильно!"
    #[should_panic(expected = "Значение должно быть от 1 до 100")] 
    fn greater_than_100() {
        // Передаем 200, ожидаем панику внутри функции new
        Guess::new(200); 
    }
}
```

*Зачем нужен `expected`?* Он проверяет, что функция упала именно с *этим* сообщением об ошибке, а не по какой-то другой, случайной причине.

#### 3. Интеграционные тесты

Юнит-тесты находятся внутри твоих файлов `src/`. Они имеют доступ к скрытым, приватным функциям (без слова `pub`) и тестируют "внутренности" механизма.

**Интеграционные тесты** тестируют твою программу *снаружи*, точно так же, как её использовал бы другой разработчик. 
Для них мы создаем специальную папку `tests/` на одном уровне с папкой `src/`.

Структура:
```text
my_project/
├── Cargo.toml
├── src/
│   └── lib.rs
└── tests/
    └── integration_test.rs
```

Внутри `integration_test.rs` нам больше не нужен атрибут `#[cfg(test)]`. Этот файл и так является тестовым. Мы просто подключаем наш проект как внешнюю библиотеку и тестируем её публичный интерфейс.

```rust
// Подключаем наш проект (название берется из Cargo.toml)
use my_project; 

#[test]
fn test_public_api() {
    assert_eq!(my_project::add_two(2), 4);
}
```

#### 4. rustdoc: Документация как код

В мире программирования есть старая проблема: код обновляется, а документация к нему устаревает, потому что программисты забывают её переписывать. Документация начинает врать.

Rust решает это гениально. Документация пишется прямо в коде специальными комментариями с тремя слешами: **`///`**. Она поддерживает разметку Markdown (как в Telegram или на GitHub).

```rust
/// Вычисляет зарплату после вычета налогов.
///
/// # Примеры
///
/// ```
/// let salary = 100_000.0;
/// let final_salary = my_project::calculate_net_salary(salary);
/// assert_eq!(final_salary, 87_000.0);
/// 
///
/// # Ошибки
///
/// Эта функция вызовет `panic!`, если передана отрицательная зарплата.
pub fn calculate_net_salary(gross: f64) -> f64 {
    if gross < 0.0 {
        panic!("Зарплата не может быть отрицательной");
    }
    gross * 0.87 // Вычитаем 13%
}
```

**Магия №1: Генерация сайта.**
Если ты напишешь в терминале команду:
```bash
cargo doc --open
```
Cargo соберет все твои комментарии `///`, красиво их отформатирует и автоматически откроет в твоем браузере потрясающий, удобный веб-сайт с документацией твоего проекта (и документацией всех библиотек, которые ты используешь!). Тебе не нужно настраивать дизайн — всё генерируется само.

**Магия №2: Доктесты (Doctests).**
Посмотри на раздел "Примеры" в комментарии выше. Мы написали там кусок кода в "кавычках" `Markdown ()`.

Когда ты запускаешь команду `cargo test`, компилятор Rust делает нечто невероятное: он **находит все примеры кода внутри твоей документации, компилирует их и запускает как настоящие тесты**. 

Если ты изменишь логику функции, но забудешь обновить пример в документации — команда `cargo test` выдаст ошибку! В Rust документация *физически не может* врать или содержать нерабочий код. Это одна из самых любимых фич языка среди сеньоров.
