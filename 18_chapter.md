### Глава 18. Многопоточность (Concurrency)

#### 1. Создание потоков и передача Владения (`move`)

Операционная система умеет выполнять несколько "потоков" (нитей) выполнения одновременно, распределяя их по разным ядрам твоего процессора.

Чтобы запустить новый поток в Rust, мы используем функцию `thread::spawn` и передаем ей **замыкание** (код, который должен выполниться в новом потоке).

```rust
use std::thread;
use std::time::Duration;

fn main() {
    // Создаем новый поток
    let handle = thread::spawn(|| {
        for i in 1..=5 {
            println!("Привет из нового потока! Номер: {}", i);
            // Усыпляем поток на миллисекунду, чтобы дать поработать другим
            thread::sleep(Duration::from_millis(1)); 
        }
    });

    for i in 1..=3 {
        println!("Привет из ГЛАВНОГО потока! Номер: {}", i);
        thread::sleep(Duration::from_millis(1));
    }

    // ВАЖНО: Если главный поток (main) завершится, 
    // все остальные потоки будут мгновенно убиты, даже если не доработали.
    // Метод join() ставит главный поток на паузу и заставляет его 
    // ДОЖДАТЬСЯ завершения созданного потока (handle).
    handle.join().unwrap(); 
}
```

**Проблема с захватом переменных:**
Что, если мы хотим передать данные из главного потока в новый?
```rust
let v = vec![1, 2, 3];

let handle = thread::spawn(|| {
    // ОШИБКА КОМПИЛЯЦИИ! Компилятор скажет: "А вдруг поток проживет 
    // дольше, чем вектор v? Ссылка станет недействительной!"
    println!("Вектор: {:?}", v); 
});
```
Чтобы это починить, мы должны использовать ключевое слово **`move`** перед замыканием. Оно заставляет замыкание **навсегда забрать Владение (Ownership)** вектором `v` в новый поток.

```rust
let v = vec![1, 2, 3];
let handle = thread::spawn(move || { // Теперь вектор ЖИВЕТ внутри этого потока
    println!("Вектор: {:?}", v);
});
```

#### 2. Разделение состояния: Мьютексы (`Mutex`)

Что делать, если несколько потоков должны *изменять* одну и ту же переменную? 
Представь конференцию. На сцене стоит один микрофон. Чтобы что-то сказать, ты должен подойти, **захватить микрофон**, сказать свою речь, а затем **освободить микрофон** для следующего. Если два человека начнут говорить в микрофон одновременно, будет шум.

Этот микрофон называется **Mutex** (Mutual Exclusion — взаимное исключение). Он разрешает доступ к данным только одному потоку в любой момент времени.

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(5); // Прячем число 5 внутрь Мьютекса

    {
        // lock() блокирует поток до тех пор, пока микрофон не освободится.
        // Когда мы получаем блокировку, мы можем безопасно менять данные.
        let mut num = m.lock().unwrap();
        *num = 6; 
        
    } // МАГИЯ! Когда переменная num выходит из области видимости, 
      // срабатывает трейт Drop, и микрофон АВТОМАТИЧЕСКИ освобождается!
      // В Rust невозможно "забыть" разблокировать Mutex.

    println!("Мьютекс: {:?}", m);
}
```

#### 3. Многопоточный подсчет ссылок: Смарт-указатель `Arc`

В прошлой главе мы изучили `Rc` (указатель, считающий ссылки), чтобы разрешить нескольким владельцам читать данные. 
Почему бы нам не упаковать `Mutex` в `Rc` и не раздать потокам?

```rust
// let counter = Rc::new(Mutex::new(0)); 
// ОШИБКА! Компилятор запретит это!
```
Дело в том, что `Rc` не является потокобезопасным (Thread-safe). Если два потока попытаются одновременно увеличить его внутренний счетчик (который работает без мьютекса), счетчик сломается, и мы получим утечку памяти или краш.

Для многопоточности придуман брат-близнец `Rc` — **`Arc` (Atomic Reference Counted)**. Его счетчики изменяются "атомарно" (на уровне процессора, их невозможно прервать). Он чуть медленнее обычного `Rc`, но абсолютно безопасен.

**Святой Грааль Rust (`Arc<Mutex<T>>`):** Эта связка используется в 90% случаев, когда нужно разделить изменяемое состояние между потоками.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // Оборачиваем счетчик в Мьютекс (для безопасного изменения), 
    // а затем в Arc (для безопасного размножения владельцев по потокам).
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        // Создаем локальную копию указателя Arc для каждого потока
        let counter_clone = Arc::clone(&counter);
        
        let handle = thread::spawn(move || {
            // Захватываем микрофон и увеличиваем счетчик
            let mut num = counter_clone.lock().unwrap();
            *num += 1;
        });
        handles.push(handle);
    }

    // Ждем завершения всех 10 потоков
    for handle in handles {
        handle.join().unwrap();
    }

    // Результат ГАРАНТИРОВАННО будет 10. Никаких гонок данных!
    println!("Итог: {}", *counter.lock().unwrap());
}
```

#### 4. Взаимоблокировки (Deadlocks)

Rust защищает от гонок данных, но **не защищает** от Дедлоков. 
Взаимоблокировка происходит, когда Поток А захватил `Mutex 1` и ждет `Mutex 2`, а Поток Б захватил `Mutex 2` и ждет `Mutex 1`. Два упрямых барана встретились на узком мосту и заблокировали программу навсегда.

Чтобы избежать этого, всегда захватывай Мьютексы в строго одинаковом порядке во всех потоках, или используй более умные подходы, такие как каналы.

#### 5. `RwLock` (Чтение-Запись)

Иногда данные читают очень часто, а меняют редко. `Mutex` блокирует данные даже для простых читателей, заставляя их ждать в очереди. 
**`RwLock` (Read-Write Lock)** работает как маркерная доска в офисе:
*   Любое количество потоков может читать (`.read()`) доску одновременно (ведь они не мешают друг другу).
*   Но если кто-то хочет написать на доске (`.write()`), он должен дождаться, пока все читатели уйдут, и заблокировать доску только для себя.

#### 6. Межпотоковое взаимодействие через каналы (Channels)

В современной разработке (и особенно в языке Go) есть мощная мантра: 
*"Не общайтесь, разделяя память. Разделяйте память, общаясь"*.

Вместо того чтобы возиться с `Arc<Mutex>` и рисковать дедлоками, потоки могут просто пересылать друг другу сообщения через **Каналы**.



Канал — это труба с водой. С одной стороны сидят отправители (Producers) и бросают в воду бумажные кораблики с данными. С другой стороны сидит один получатель (Consumer) и вылавливает их.
В Rust это называется **`mpsc` (Multi-Producer, Single-Consumer)**.

```rust
use std::sync::mpsc;
use std::thread;
use std::time::Duration;

fn main() {
    // Создаем канал. Он возвращает кортеж (Отправитель, Получатель)
    // tx = transmitter, rx = receiver
    let (tx, rx) = mpsc::channel();

    // Передаем Владение отправителем (tx) в новый поток
    thread::spawn(move || {
        let val = String::from("Привет из глубины");
        // Отправляем сообщение в канал
        tx.send(val).unwrap(); 
        // ВАЖНО: После send() переменная val перемещена (move) в канал! 
        // Мы больше не можем её использовать в этом потоке. Это гарантирует безопасность.
    });

    // Главный поток блокируется и ждет (recv - receive), 
    // пока по трубе не приплывет сообщение
    let received = rx.recv().unwrap();
    println!("Получено: {}", received);
}
```
Каналы невероятно удобны для архитектуры типа "Главный поток управляет интерфейсом, а 5 рабочих потоков (воркеров) скачивают файлы и присылают статусы по каналу".

#### 7. Продвинутые примитивы синхронизации (Кратко)

*   **Атомарные типы (`AtomicUsize`, `AtomicBool`):** Если тебе нужно просто считать лайки в многопоточной среде (увеличивать число), `Mutex` будет слишком медленным. Атомарные типы используют специальные инструкции самого процессора (CPU), чтобы изменять числа мгновенно и безопасно без всяких блокировок.
*   **Барьеры (`Barrier`):** Представь забег. Потоки добегают до барьера и останавливаются. Ни один поток не побежит дальше, пока к барьеру не придут *все* остальные. 
*   **Thread Local Storage (TLS):** Это глобальные переменные, у которых для *каждого* потока есть своя собственная, независимая копия. Поток А меняет переменную, а Поток Б этого даже не видит.
