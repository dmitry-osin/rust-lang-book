### Глава 13. Время жизни ссылок (Lifetimes)

Каждая ссылка в Rust имеет срок годности (время жизни). Это отрезок времени, в течение которого данные, на которые она указывает, остаются в памяти. 
В 90% случаев компилятор сам вычисляет этот срок (как он сам вычисляет типы переменных). Но иногда код становится слишком сложным, и компилятор впадает в ступор. Тогда мы должны ему помочь.

#### 1. Проблема: Когда компилятор слепнет

Представь, что мы пишем функцию, которая принимает две строки и возвращает самую длинную из них. Мы не хотим передавать владение (строки нам еще понадобятся), поэтому мы передаем **ссылки**.

```rust
// ОШИБКА КОМПИЛЯЦИИ! Этот код не соберется.
fn longest(x: &str, y: &str) -> &str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}
```

Почему компилятор ругается? 
Посмотри на это глазами компилятора: *"Мне передали две ссылки. Я должен вернуть одну ссылку. Но я не знаю, ЧЬЮ ИМЕННО ссылку я верну: x или y (ведь это решается внутри `if` во время работы программы). А вдруг данные `y` удалятся из памяти раньше, чем данные `x`? Как мне гарантировать безопасность?"*

Компилятор требует, чтобы мы **явно связали** время жизни входных параметров и результата.

#### 2. Аннотации времени жизни в функциях

Чтобы связать ссылки, мы используем аннотации времени жизни. Они всегда начинаются с апострофа и пишутся маленькими буквами. Самая популярная буква — **`'a`** (читается как "лайфтайм а"). 

Это похоже на работу с дженериками: мы сначала объявляем `'a` в угловых скобках `< >`, а потом "развешиваем" этот ярлык на нужные ссылки.

```rust
// Читается так: "Эта функция использует некое время жизни 'a.
// Ссылка x живет не меньше 'a.
// Ссылка y живет не меньше 'a.
// И возвращаемая ссылка ТОЖЕ будет жить не меньше 'a".
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}

fn main() {
    let string1 = String::from("очень длинная строка");
    let result;
    
    {
        let string2 = String::from("короткая");
        // Вызываем функцию. Компилятор смотрит:
        // string1 живет долго (до конца main)
        // string2 живет мало (до конца этих фигурных скобок)
        // Компилятор берет НАИМЕНЬШЕЕ из них и назначает его как 'a.
        result = longest(&string1, &string2); 
    } // ЗДЕСЬ string2 удаляется из памяти! А вместе с ней заканчивается и срок 'a.

    // println!("Самая длинная: {}", result); 
    // ОШИБКА КОМПИЛЯЦИИ! Если раскомментировать println!, компилятор ударит по рукам.
    // result связан сроком годности 'a (который умер вместе со string2). 
    // Мы пытаемся использовать просроченную ссылку!
}
```

**Главный секрет Lifetimes:** Аннотации `'a` **не меняют** реальное время жизни данных. Они не заставят переменную жить дольше. Они просто *описывают отношения* между ссылками, чтобы компилятор мог правильно применить свои правила и защитить тебя от краша.

#### 3. Аннотации ссылок в структурах

До сих пор все наши структуры (например, `User` или `Point`) полностью владели своими данными (внутри были типы `String`, `i32` и т.д.).
А что, если мы хотим положить внутрь структуры **ссылку** на данные, которые лежат где-то в другом месте?

Мы обязаны указать время жизни. Иначе структура могла бы пережить данные, на которые она ссылается!

```rust
// Говорим: "Структура ImportantExcerpt не может жить дольше, 
// чем живет строка (part), на которую она ссылается ('a)".
struct ImportantExcerpt<'a> {
    part: &'a str,
}

fn main() {
    let novel = String::from("Зовите меня Измаил. Несколько лет назад...");
    
    // Мы разделяем строку по точке и берем первое предложение
    let first_sentence = novel.split('.').next().unwrap();
    
    // Создаем структуру, которая хранит ССЫЛКУ на кусок строки novel
    let i = ImportantExcerpt {
        part: first_sentence,
    };
    
    // Это безопасно, потому что novel живет до самого конца main(), 
    // а значит 'a действует, и структура i валидна.
}
```

#### 4. Аннотации ссылок в методах

Если у структуры есть аннотация времени жизни, мы должны указывать её и при написании методов в блоке `impl` (так же, как мы делали это с дженериками).

```rust
// Объявляем 'a после impl и привязываем к ImportantExcerpt
impl<'a> ImportantExcerpt<'a> {
    // В методах часто не нужно писать аннотации для возвращаемых ссылок!
    // Компилятор применяет правило: "Если есть &self, то возвращаемая ссылка 
    // получает то же время жизни, что и &self".
    fn get_part(&self) -> &str {
        self.part
    }
}
```
*Элизия (сокрытие) времени жизни:* Разработчики Rust поняли, что писать `'a` везде — это утомительно. Поэтому компилятор имеет встроенные паттерны. Если метод принимает `&self` или `&mut self`, он автоматически считает, что все возвращаемые ссылки связаны с `self`. Поэтому в 99% методов тебе не придется писать `'a` руками.

#### 5. Статическое время жизни ('static)

В Rust есть одно специальное зарезервированное имя для времени жизни — **`'static`**.
Оно означает, что данные живут **в течение всего времени работы программы** (никогда не удаляются).

Где мы это встречаем? В строковых литералах!

```rust
// Текст "Привет" "запекается" прямо в бинарный файл (exe) программы при компиляции.
// Он всегда находится в памяти, поэтому его ссылка имеет время жизни 'static.
let s: &'static str = "Привет, мир!";
```

*Важно:* Иногда компилятор при ошибках может советовать тебе добавить `'static`. В 90% случаев это плохой совет! Обычно это означает, что ты пытаешься вернуть из функции ссылку на локальную переменную, которая сейчас уничтожится (со Стека). Вместо того, чтобы делать её `'static`, тебе нужно просто вернуть само значение (передать Владение), а не ссылку на него.

---

**Резюме:**
*   Время жизни (**Lifetimes**) предотвращает использование ссылок на уже удаленные данные.
*   Если функция возвращает ссылку, компилятор должен знать, откуда она взялась. Мы используем аннотации вида **`'a`**, чтобы связать входы и выходы.
*   Структуры, хранящие ссылки, обязаны иметь аннотацию времени жизни, чтобы не пережить свои данные.
*   **`'static`** — это вечная жизнь, характерная для хардкодных строк в бинарнике.
